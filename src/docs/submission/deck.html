PS-021: Experimental Dialog Correlation
and Recovery Across Agent Adapters

Two mock agent adapters that keep task identity and never repeat recorded work —
across lost requests, lost replies and restarts.

Experimental prototype · not exactly-once · not MCP/A2A · not an IETF standard

1

The problem

  • Agents hand tasks to each other across frameworks; each tracks "which conversation is this?" its own way.
  • Mid-task, a request or a reply gets lost, or an agent restarts.
  • The sender cannot tell whether the work was done — so it retries.
  • Lost reply + retry → the work runs twice (two messages, two records, charged twice).
  • Restart with state only in memory → the task is forgotten; a retry looks like new work.
  • PS-021 asks for: dialog IDs, explicit lifecycle states, request deduplication, durable recovery — tested on five disconnect/retry scenarios.
2

Approach: name it, write it down, check before acting

IdentifierMeaningWhere it lives
dialog_idOne A↔B exchange about one task — the correlation keydialogs table (with state, restored)
task_idThe unit of work; B rejects a request whose task_id differsdialogs table
seqOne logical request; (dialog_id, seq) = the dedup keyA's send log outbound_requests · B's records requests
  • Write it down first: A logs each request PENDING before sending; every write goes to the SQLite file.
  • Check before acting: B returns the stored result if (dialog_id, seq) was already processed.
  • Schema: clearly labelled v0.1-experimental (no mentor draft pinned) — docs/EXPERIMENTAL_SCHEMA.md.

Pseudocode — Adapter B, in this order

handleRequest(req):                                     # backend/src/adapters/AdapterB.ts
    dialog = correlate(req.dialog_id, req.task_id)      # DIALOG_NOT_FOUND / TASK_MISMATCH
    if processed.has(req.dialog_id, req.seq):
        return duplicate(stored result)                 # work NOT re-run
    if dialog is terminal: return error(DIALOG_TERMINAL)
    result = run_side_effect(req.payload)               # ── crash window opens
    processed.insert(req.dialog_id, req.seq, result)    # persisted ── crash window closes
    if dialog.state == INITIATED: transition(PROCESSING)
    return ok(result)

recover():                                              # AdapterA.ts — after every restart
    for each INITIATED / PROCESSING dialog: restored = true,
        next_seq = send_log.max_seq + 1, pending_seqs = send_log.pending

10

Limitations & non-claims

  • Not exactly-once — a recorded request is never re-run; a crash between the work and its record can repeat it.
  • Not an IETF standard — experimental schema, inspired by agentproto.
  • Not MCP / A2A; no interoperability with them.
  • No interoperability between independently built adapters claimed — pending mentor clarification.
  • One process, one shared SQLite file (restart A = restart B).
  • File rewritten in place — a crash during the write could corrupt it.
  • In-process transport: drop request / drop reply only.
  • Side-effect / duplicate counters and the event log are in memory.
  • Local, unauthenticated demo API.
